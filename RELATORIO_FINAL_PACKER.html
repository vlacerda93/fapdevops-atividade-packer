PARTE I

Fundamentação Teórica: Cloud-init & HashiCorp Packer

1. O que é o Cloud-init? (Conceito, Propósito e Caso Prático)

Bootstrapping / Run Time
O que é / Para que serve

O Cloud-init é o padrão multiplataforma da indústria para inicialização e configuração automatizada de instâncias em nuvem durante o primeiro boot (Zero-Touch Provisioning). Ele funciona como um agente embutido na imagem do sistema operacional que lê metadados e scripts declarativos (user-data em YAML ou Shell) fornecidos pelo provedor (AWS, Azure, GCP, OpenStack) assim que a máquina virtual liga pela primeira vez.

Exemplo Prático na Nuvem

Ao provisionar uma instância Amazon EC2 via Terraform ou Console AWS, passamos um bloco #cloud-config no campo user-data que automaticamente: (1) cria o usuário da equipe de engenharia com permissão sudo, (2) injeta as chaves públicas SSH autorizadas, (3) formata e monta um volume EBS adicional em /data e (4) registra a instância em um agente de monitoramento (Prometheus Node Exporter) sem necessidade de nenhum acesso manual via SSH.

Regra de Ouro no Mercado

Ideal para parametrização de identidade única da máquina (hostname, IP estático, credenciais dinâmicas de cofre, registro em cluster Kubernetes) no momento em que a instância nasce.

2. O que é o HashiCorp Packer? (Funcionamento e Problema Real que Resolve)

Baking / Build Time
O que é / Como funciona

O HashiCorp Packer é uma ferramenta open-source de Infraestrutura como Código (IaC) que automatiza a criação de imagens de máquina idênticas e imutáveis (Golden Images) a partir de um único arquivo declarativo HCL (.pkr.hcl). Ele sobe uma instância ou contêiner temporário (Builder), executa scripts e copia arquivos para instalar pacotes e dependências (Provisioners), congela o estado final gerando o artefato e aplica tags/versões (Post-Processors), destruindo o ambiente provisório ao final.

Problema Real que Resolve em uma Empresa

Em uma empresa de e-commerce durante um pico de tráfego (ex.: Black Friday), se o grupo de Auto Scaling tentar criar 30 novos servidores instalando tudo do zero no boot (Apache/Nginx, runtimes Python/Node, agentes de segurança e dependências via apt ou npm), cada máquina levará 12 a 20 minutos para ficar pronta — e se um repositório externo oscilar, as novas instâncias falham. Com o Packer, a empresa aplica o conceito de Baking: a imagem já vem "assada" e testada com todo o stack pré-instalado, fazendo com que novas instâncias entrem em produção em menos de 15 segundos e com zero risco de configuration drift.

3. Análise Comparativa: HashiCorp Packer (Golden Image) vs. Cloud-init

Arquitetura Híbrida

A diferença central está no momento do ciclo de vida da infraestrutura em que cada ferramenta atua: o Packer opera em tempo de construção (Build Time) gerando um molde imutável, enquanto o Cloud-init opera em tempo de inicialização (Run Time / First Boot) customizando a instância viva.

Critério Técnico HashiCorp Packer (Baking / Golden Image) Cloud-init (Bootstrapping / First Boot)
Momento de Execução Build Time (Pré-Deploy): Executado na esteira de CI/CD antes de qualquer servidor subir em produção. Run Time (Primeiro Boot): Executado quando a máquina virtual é ligada pela primeira vez na nuvem.
Artefato Gerado Gera uma imagem imutável (AWS AMI, Azure VHD, imagem Docker) pronta para ser replicada. Configura uma instância específica em execução a partir de metadados (user-data).
Velocidade de Escalonamento Ultrarrápida (segundos): Os binários, bibliotecas e arquivos já estão gravados no disco da imagem. Mais lenta (minutos) caso seja usado para baixar pacotes pesados via rede a cada boot.
Repetibilidade & Segurança Garante 100% de paridade entre Dev, Stage e Prod; vulnerabilidades e testes são validados antes de publicar a imagem. Suscetível a falhas de rede ou mudanças de versão de pacotes externos se instalar dependências em tempo real.
Uso Combinado no Mercado Padrão Ouro DevOps: Usa-se o Packer para embutir 95% do peso estático (SO atualizado, hardening, runtime, servidor web, dependências) na Golden Image, e o Cloud-init apenas nos 5% finais dinâmicos que mudam de máquina para máquina (hostname, variáveis de ambiente de produção e chave de registro no cluster).

Atividade 1: Servidor Web Apache com Injeção de Arquivo Local

Diretório: desafio1/ • Imagem gerada: meu-apache-packer:latest (ID: 75d94801f0d9)

Nível Iniciante • Validado
Arquitetura da Receita & Ordem dos Provisioners

Partindo da imagem base ubuntu:jammy com metadados EXPOSE 80 e CMD ["apachectl", "-D", "FOREGROUND"] no bloco changes, o primeiro provisioner (shell) instala o pacote apache2 — garantindo a criação do diretório /var/www/html/. Só então o segundo provisioner (file) injeta o index.html local para dentro da imagem, finalizando com o post-processor "docker-tag".

desafio1/desafio1.pkr.hcl HCL Template 
packer {
  required_plugins {
    docker = {
      version = ">= 1.0.8"
      source  = "github.com/hashicorp/docker"
    }
  }
}

source "docker" "ubuntu" {
  image  = "ubuntu:jammy"
  commit = true
  changes = [
    "EXPOSE 80",
    "CMD [\"apachectl\", \"-D\", \"FOREGROUND\"]"
  ]
}

build {
  name    = "meu-apache"
  sources = ["source.docker.ubuntu"]

  provisioner "shell" {
    inline = [
      "apt-get update",
      "DEBIAN_FRONTEND=noninteractive apt-get install -y apache2",
      "apt-get clean"
    ]
  }

  provisioner "file" {
    source      = "index.html"
    destination = "/var/www/html/index.html"
  }

  post-processor "docker-tag" {
    repository = "meu-apache-packer"
    tags       = ["latest"]
  }
}

Atividade 2: Ambiente Base Padronizado para Python + Flask

Diretório: desafio2/ • Imagem gerada: ambiente-dev-python:v1 (ID: 86d13d7dab4a)

Nível Intermediário • Validado
Decisões Técnicas & Otimização de Imagem

Definido o diretório padrão de trabalho WORKDIR /app via atributo changes do builder Docker. Na instalação via apt-get, foi aplicada a flag --no-install-recommends junto com pip install --no-cache-dir Flask e apt-get clean, evitando o download de mais de 340 MB de compiladores C/C++ desnecessários e mantendo a imagem enxuta.

desafio2/desafio2.pkr.hcl HCL Template 
packer {
  required_plugins {
    docker = {
      version = ">= 1.0.8"
      source  = "github.com/hashicorp/docker"
    }
  }
}

source "docker" "python_base" {
  image  = "ubuntu:jammy"
  commit = true
  changes = [
    "WORKDIR /app"
  ]
}

build {
  name    = "dev-python"
  sources = ["source.docker.python_base"]

  provisioner "shell" {
    inline = [
      "apt-get update",
      "DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends python3 python3-pip ca-certificates",
      "mkdir -p /app",
      "pip install --no-cache-dir Flask",
      "apt-get clean"
    ]
  }

  post-processor "docker-tag" {
    repository = "ambiente-dev-python"
    tags       = ["v1"]
  }
}

Atividade 3: Ambiente Node.js com Pipeline em Múltiplos Passos

Diretório: desafio3/ • Imagem gerada: ambiente-node:v1 (ID: 27b402fb574a)

Nível Intermediário • Validado
Encadeamento Sequencial de Provisioners

Demonstra a execução determinística em três estágios: (1) provisioner shell instala nodejs e npm e cria o diretório /app; (2) provisioner file transfere o arquivo local package.json (contendo {}) para /app/package.json; e (3) segundo provisioner shell executa cd /app && npm install, gerando o package-lock.json auditado dentro da imagem imutável.

desafio3/desafio3.pkr.hcl HCL Template 
packer {
  required_plugins {
    docker = {
      version = ">= 1.0.8"
      source  = "github.com/hashicorp/docker"
    }
  }
}

source "docker" "node_base" {
  image  = "ubuntu:jammy"
  commit = true
}

build {
  name    = "dev-node"
  sources = ["source.docker.node_base"]

  provisioner "shell" {
    inline = [
      "apt-get update",
      "DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends nodejs npm ca-certificates",
      "mkdir -p /app",
      "apt-get clean"
    ]
  }

  provisioner "file" {
    source      = "package.json"
    destination = "/app/package.json"
  }

  provisioner "shell" {
    inline = [
      "cd /app && npm install"
    ]
  }

  post-processor "docker-tag" {
    repository = "ambiente-node"
    tags       = ["v1"]
  }
}
